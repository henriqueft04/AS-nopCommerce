# Critique

## What helped and what got in the way

nopCommerce has one architectural decision that made instrumentation significantly easier than it had any right to be: `EntityRepository<TEntity>`. Every single data operation across all 40-plus service domains flows through this one generic class. Putting spans in four methods there(get, insert, update, delete) gave visibility to the database-level across the entire application without touching a single service file for that purpose. That kind of structural chokepoint makes life easier, and it may not have been designed with observability in mind. It is just good layering that happens to be instrumentation-friendly.

The `INopStartup` discovery mechanism was equally helpful. Rather than modifying the existing startup pipeline, I could drop a new class implementing the interface and set its order to -5. The framework picks it up automatically via reflection. The OTel SDK was registered before anything else ran, and nothing existing was touched.

The .NET BCL's own `System.Diagnostics.ActivitySource` and `System.Diagnostics.Metrics` being independent of the OTel SDK also mattered. I could place `NopActivitySource` and `NopMetrics` in `Nop.Core`, which has no outbound dependencies, making them available to `Nop.Data` and `Nop.Services` without pulling OTel packages into those projects. The SDK wires itself up at startup in `Nop.Web.Framework` and hooks into the BCL primitives from there. No version coupling, no circular dependencies.

The .NET and nopCommerce toolchain itself created issues that had nothing to do with the instrumentation work. The dotnet CLI was unfamiliar territory for me. The build and run sequence (restore, build, run as separate commands) is straightforward once you know it, but nopCommerce adds a step that is not obvious from the repository, the first time you start the application, it serves a setup wizard that must be completed through the browser before the app functions at all. Nothing in the repository surface makes this clear, and the app starts successfully and listens on port 5000 whether or not setup has been completed, so there is no obvious failure signal.

Configuration was a similar trap. nopCommerce does not load `appsettings.json` from the project root at runtime. It loads from `App_Data/appsettings.json`. This means the standard ASP.NET Core mental model — put config in `appsettings.json` — does not apply. The OTel endpoint was placed in the wrong file initially, which caused the exporter to fall back silently to defaults and send nothing. There was no error, no warning, just an absence of data in the collector. Diagnosing a silent misconfiguration in a system you are still learning is significantly harder than diagnosing an explicit failure.

The OTLP transport added another layer of friction. The gRPC exporter (port 4317) is the default and the most commonly documented option, but it requires a native gRPC channel that was not available in this environment. Switching to HTTP/protobuf (port 4318) resolved it, but that switch is not mentioned in the standard OTel .NET quickstart guides. Port conflicts were also a recurring issue: old app processes left running on port 5000 would prevent new instances from starting, and the only indication is a binding failure at startup.


What genuinely got in the way was the logging layer. nopCommerce ships its own `DefaultLogger` that writes to a database table. It does not implement `Microsoft.Extensions.Logging.ILogger`, which means it is completely invisible to the OTel log pipeline. You cannot bridge it through configuration, you would need to modify the logger itself to dual-write into MEL. The result is that traces and metrics work but the log signal is absent. That is a significant gap for a production system where logs are often the first thing we cehck.

The `IEventPublisher` mechanism presents a subtler problem. Events are published fire-and-forget into a list of registered consumers. The OTel trace context, the `Activity` that represents the current operation, does not automatically propagate into event handlers. If a consumer does significant work in response to an event, that work is invisible in the trace. It appears to complete instantly from the caller's perspective. For the search-and-pricing flow this was not critical because the work I cared about is synchronous. But for order placement, where events trigger inventory reservation and notification dispatch, this would produce traces that fundamentally misrepresent the actual work being done.

## What I would change going forward

The single highest-value architectural change would be replacing `DefaultLogger` with a thin adapter that writes to `Microsoft.Extensions.Logging.ILogger<T>` and lets the OTel log exporter handle the rest. The existing database logging behaviour can be preserved by adding a custom `ILoggerProvider` that writes to the same table. The cost is lowm and the benefit is that logs, traces, and metrics become correlated through the same trace ID. Right now you can see a slow request in Jaeger and a spike in Prometheus but you cannot find the log lines that go with them without searching by timestamp.

The second change I would make is adding trace context propagation to `IEventPublisher`. The simplest approach is to capture `Activity.Current` at publish time and restore it at consume time using `Activity.SetParentId`. This does not require changing the event system's interface at all -- it is a change to the dispatcher internals only. The result is that async event-driven work becomes visible as child spans of the operation that triggered it, which is the correct representation.

I would not instrument the plugin layer directly. The HttpClient instrumentation already captures outbound calls to payment providers and shipping APIs at the transport level, which gives latency and error visibility. Reaching into plugin assemblies to add business-level spans would mean accepting a maintenance burden across 30-plus independent projects every time nopCommerce updates. The transport boundary is the right place to stop.

## Where the surgical changes landed

The two places where I had to touch business logic rather than infrastructure were `ProductService.SearchProductsAsync` and `PriceCalculationService.GetFinalPriceAsync`. In both cases the reason was the same: I needed the output of the method, the result count and whether a discount was applied to record meaningful metrics. That information only exists at the point of return, not at a wrapping boundary.

In `SearchProductsAsync` the method had two separate return statements for different result paths. I merged them into a single variable assignment so the histogram could be recorded once before returning. The change was four lines and did not alter the logic. In `GetFinalPriceAsync` I added a span and a counter around an existing operation that was already clearly scoped.

The assignment's guidance says to keep changes as close to the infrastructure boundary as possible and not in business logic. I agree with that in principle, and I followed it for the database layer. But for metrics that reflect business-level outcomes, how many products came back, whether a discount fired, there is no infrastructure boundary that has that information. The service method is the right place, and the right response is to keep the changes minimal and leave the logic untouched, which is what I did.
